# 0004：持久化发布计划、成功边界与先发后删

## 状态

已接受。本轮实现失败隔离并增加模拟网关回归；旧提交不包含这些保障。验证范围限于本地模拟网关，不宣称已完成真实 Telegram 验证。

## 背景

**历史事实**：引擎在 SQLite 保存发送批次、消息映射和清理进度；先发送所有新批次，再发布归档映射，最后清理旧内容。发送采用可重用的固定标识，收到不确定结果时不冒充成功。

**推断动机**：Telegram 与 SQLite 无分布式事务，必须显式区分暂存、归档成功和清理完成，避免旧版提前删除或失败状态污染后续业务。

## 决策

- 规划前业务状态作为 undo 持久化。pending 期间串行业务不越过；发送和映射成功前，新 record、Hash、人工种子及历史 route/DOWN 变更仍为暂存状态，不是可用于后续分类的成功历史。
- 全部新批次发送成功且映射事务发布后，才算归档成功。此前若终态失败，撤回本任务新增 record/Hash/人工种子及历史 route/DOWN 变更，防止后续任务隐式补发失败任务。
- 已发送的部分批次保留在失败计划中供 MAN 人工检查；不自动清理，也不自动续发。保留旧有效版本，不把业务状态回滚误称为 Telegram 消息回滚。
- 归档成功后才清理 ONESHOT、旧 UP 版本及已替代人工 UP 输入，不清理旧 REPEAT。此后清理终态失败不撤销成功归档；报 MAN 并保留失败清理计划。
- 旧格式失败计划缺少 undo 时，尝试依据已发布的 `archives` / `up_groups` 恢复状态；这是兼容性恢复，不承诺无损推导任意旧中间状态。
- 启动时若发现未隔离的旧格式失败历史，同时存在未发布的待续发计划，将该计划也终止并交 MAN，避免依据污染历史继续发布。若失败输入后来已被其他旧计划成功归档，保留该成功历史，不自动重算此前已发布结果。

以上失败边界是**本轮澄清与修复约定**，不是对 5047af0 行为的完整描述。

## 替代方案

先删后发可能永久丢失有效展示；仅在内存记录进度不能重启恢复；把所有失败都视为成功历史会导致后续任务隐式补发。自动清除部分新批次或自动续发终态失败均不采用，交由 MAN 检查。

## 后果与局限

pending 重试可恢复，终态失败则停止该业务计划的自动执行；两者不能混称“重启续发”。固定 `random_id` 只能降低重复风险，Telegram 去重窗口有限，不保证任意延迟下绝对 exactly-once。发送成功但响应丢失仍可能留下人工检查项。失败任务、输入、发送及清理进度仍在 jobs 中，撤回暂存 records 不会删除失败证据或本地原件。

模拟网关回归覆盖普通及人工失败的历史隔离、UP 半成品在重启后的保留且不隐式重发、发布后清理失败、以及旧格式失败后无后续计划/存在待续发计划/已被后续计划成功归档三种升级情况。上线前应停服备份数据库与媒体；这些测试不代表已修复线上历史消息，也不保证重算旧污染产生的所有成功分类。
