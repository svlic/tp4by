# 0006：事件去重、启动补录与 MAN

## 状态

已接受当前接收与异常出口；首次历史导入是否需要另行支持仍未决。

## 背景

**历史事实**：在线相册与单条消息分开接收；事件键由频道与相册 ID 或消息 ID 构成，SQLite 唯一约束避免重复建档。启动回看可能与在线消息重叠。

**推断动机**：持久化游标加事件去重，使离线补录与在线监听共存；MAN 使不能自动完成的输入仍有可追踪出口。

## 决策

- 当前首次启动从频道末尾建立基线，不自动导入更早历史。这是当前实现，不表示“首次历史导入不需要”已最终确认。
- 后续启动按游标和重叠窗口回看、重组相册；启动期间缓存在线输入，合并排序后入队，再推进游标。长期运行后重启可能扫描较多已处理消息，唯一事件键跳过重复。
- 启动历史按 Telegram 时间排序，同秒跨频道无严格全局顺序；在线处理顺序不宣称是跨频道的全局时间序。
- 解析/业务校验错误直接失败报 MAN；技术错误指数退避，默认上限 5 次，耗尽后报 MAN。FloodWait 按服务器等待时间，不消耗普通重试次数。
- MAN 发送错误说明和原始输入转发，不提供恢复指令。通知和转发进度分别持久化；MAN 发送失败保留待投递状态，通常 60 秒后再试，FloodWait 按服务器时间。
- **本轮澄清**：失败输入不进入成功历史；未发布终态失败与已发布清理失败分别处理，见 [0004](0004-durable-publication.md)。

## 替代方案

只监听在线事件会漏掉停机期间输入；每次导入全部历史会改变启动成本及当前首次基线业务；只记录日志会失去 MAN 人工检查出口。MAN 自动恢复指令不在当前范围。

## 后果与局限

事件去重不等于远端发送绝对 exactly-once。原消息删除或内容保护可能阻止 MAN 转发；错误通知可先保留，原件转发仍持续等待。人工删消息无监听恢复，不自动补发。

相册补齐依赖 Telethon 事件及邻近消息扫描，没有独立的期望成员数或结束标记。若首次准备时成员尚不可见，是否可能漏录仍需真实服务时序验证；现有模拟测试只证明可见邻居补齐及混组拒绝，不把该潜在风险写成线上已发生的 Bug。
