# 0005：UP 展示签名、原件与最早可读副本

## 状态

已接受，沿用当前展示业务；不定义 UP 聚合整体转 DOWN。

## 背景

**历史事实**：多个记录可连成同一 UP 集合，但成员关系变化不一定改变可见媒体和编号。媒体原件长期保存在本地；同一业务 Hash 可能有多个原件副本。

**推断动机**：分离成员身份与展示签名，可避免每次关系变化都重发；保留多副本可提高最早原件不可读时的恢复能力。

## 决策

- 对连通集合按 Writer 首次记录顺序展示，媒体按 Hash 去重，编号去重；不按编号数值或图像质量排序。
- 展示签名由编号文本和有序媒体 Hash 列表形成，不包含本地路径或成员 ID。展示未变只更新成员关系，不重发；桥接两个集合时合并重建。
- 为每个展示媒体保留按业务顺序排列的副本，发送时选最早可读副本；不是“总选最早路径”，也不是选择最高分辨率。
- 保留原件与 photo/document 形式，不主动缩图、转码。每批最多 10 项，文件相册与图片/视频相册分开且不改变媒体顺序；各媒体批次首项 caption 带完整编号。
- 编号文本超 1024 字符限制时改独立文本；超过 4096 时按编号边界分段。新展示完成发布后再清理旧版，失败边界见 [0004](0004-durable-publication.md)。

## 替代方案

按成员 ID 签名会在展示不变时重复发送；按路径签名会让缓存变化变成业务变化；优先高质量副本会改变既有首次顺序，不采用。

## 后果与局限

原件不自动删除，需监测磁盘并与数据库整体备份。最早“可读”不等于最佳质量或 Telegram 必然可发送；本地副本全失时会失败并进入重试/MAN。相同 pHash 的不同字节仍按同一业务媒体展示，其碰撞风险见 [0002](0002-record-number-hash.md)。
